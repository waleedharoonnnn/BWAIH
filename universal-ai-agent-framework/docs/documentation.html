What is AgentTest?

AgentTest is a web-based framework for testing AI agents. Think of it like a testing lab — you point it at any AI agent (a chatbot, a tool-using LLM, a RAG pipeline), give it questions to ask, and it tells you whether the agent responded correctly, used the right tools, and gave a semantically accurate answer.

Just like software engineers write unit tests for their code, AI engineers need a way to test their agents systematically. AgentTest provides that infrastructure — without writing a single line of test code.

💡
In simple terms

You tell AgentTest what your AI agent should do. AgentTest calls your agent, observes what it actually does, and scores it — automatically.

🔬
Test any AI Agent

Works with any agent that accepts a POST request. No SDK required.

⚡
Real-time Results

Live streaming feed shows each test as it runs — step by step.

🧠
AI-Powered Scoring

Uses Groq LLMs to judge whether responses are semantically correct.

📊
Rich Reports

Pass rates, semantic scores, tool traces, and assertion breakdowns.

The Problem We Solve

AI agents are being deployed faster than ever, but there is no standardized way to verify that they behave correctly. Teams face three specific challenges:

Challenge 1 — Behaviour is Non-Deterministic

Unlike traditional software, AI agents don't always produce the same output for the same input. You can't just compare strings. A correct answer can be worded many different ways.

Challenge 2 — Tool Use is Hard to Verify

Many modern agents use tools (search, APIs, databases). Verifying that an agent called the right tools, in the right order, with the right parameters requires dedicated infrastructure.

Challenge 3 — No Visibility into Reasoning

When an agent fails, it's hard to know why. Did it hallucinate? Did it skip a tool? Did it misunderstand the prompt? Without execution traces, debugging is guesswork.

✅
AgentTest solves all three

Semantic similarity scoring handles non-determinism. The assertion engine verifies tool use. Execution traces give full visibility into every agent decision.

How It Works — User Journey

Using AgentTest follows a simple 5-step workflow:

Step 1
Create Suite
→
Step 2
Add Test Cases
→
Step 3
Run Suite
→
Step 4
Watch Live Feed
→
Step 5
Read Report

Step 1 — Create a Test Suite

A Test Suite is a collection of test cases that all test the same AI agent. You configure it with:

  • Agent URL — the HTTP endpoint of your AI agent
  • Auth Key — optional Bearer token if your agent is authenticated
  • Judge Model — which Groq LLM to use for semantic scoring

Step 2 — Add Test Cases

Each Test Case defines one specific scenario to test. For each case you can specify:

  • Trigger Prompt — the exact prompt sent to your agent
  • Expected Tool Sequence — the tools your agent should call, in order
  • Golden Response — the ideal expected response (for semantic scoring)
  • Assertions — specific rules that must pass (e.g. tool was called, step limit)

Step 3 — Run the Suite

Click "Run Suite". AgentTest creates a run record in the database and starts streaming test execution in real time.

Step 4 — Watch the Live Feed

A Server-Sent Events (SSE) stream pushes updates to your browser as each test runs. You see each test's status, tool trace, assertions, and semantic score appear live.

Step 5 — Read the Full Report

After completion, a full report shows every test result with tool sequence diffs, assertion breakdowns, and a golden-vs-actual response comparison.

Core Features

Test Suites & Test Cases

The primary organizational unit is the Test Suite. A suite maps to one AI agent and contains multiple Test Cases. Each test case is a self-contained scenario with its own prompt, expected behavior, and pass/fail criteria.

Live Run Streaming

Test execution is streamed in real time using Server-Sent Events (SSE). The browser receives events as they happen — no polling required. Each event corresponds to a step: agent called, trace captured, assertions evaluated, semantic scored, test completed.

Execution Trace Viewer

Every agent call produces a detailed execution trace: an ordered list of tools the agent called, with the parameters passed to each tool and the result returned. This trace is stored in the database and visualized in the report.

Dark Mode + Light Mode

The entire UI supports system-preference dark/light mode switching with a 3-state toggle (Light → Dark → System) in the sidebar. All colors use CSS custom properties, so there are no hardcoded colors anywhere in the interface.

Dashboard with Charts

The dashboard shows aggregate stats (total suites, test cases, runs, average pass rate) with two live charts: a pass rate bar chart across the last 8 runs, and a trend area chart showing pass rate over time.

Agent Comparison

The Compare page lets you select two completed runs and benchmark them head-to-head across 5 dimensions: Accuracy, Semantic Quality, Token Efficiency, Step Speed, and Overall Score.

5

Assertion Engine

Assertions are deterministic rules that must pass for a test case to succeed. They check concrete, measurable properties of the agent's behavior — independent of AI scoring.

There are 6 assertion types:

tool_called Verifies that a specific tool was called at any point
Value: the tool name, e.g. search_kb
Example: Assert that the agent called classify_intent at least once.
tool_order Verifies that tools were called in a specific sequence
Value: comma-separated tool names in expected order, e.g. classify_intent, generate_response
Example: The agent must classify intent before generating a response.
step_limit Verifies the agent completed within a maximum number of steps
Value: a number, e.g. 3
Example: The agent must complete its task in 3 tool calls or fewer.
param_type Verifies a tool parameter is of the correct data type
Value: tool_name:param_name:type — e.g. search_kb:query:string
Example: The query parameter passed to search_kb must be a string.
output_contains Verifies the agent's final response contains a specific string
Value: the expected string, e.g. escalated
Example: The response must contain the word "escalated" for a ticket escalation test.
output_not_contains Verifies the agent's final response does NOT contain a specific string
Value: the forbidden string, e.g. error
Example: The response must not contain the word "error" in a success scenario.
🔧
Multiple assertions per test case

Each test case can have any number of assertions. All must pass. Each assertion can optionally have a description explaining what it checks, which is displayed in the report.

LLM-as-a-Judge Semantic Scoring

Beyond deterministic assertions, AgentTest uses a Groq-powered language model as a judge to score whether the agent's actual response is semantically similar to the expected golden response.

How It Works

After the agent responds, AgentTest sends three pieces of information to the judge model:

  • The original prompt (what the user asked)
  • The golden response (what the ideal answer looks like)
  • The actual response (what the agent actually said)

The judge returns a JSON object with a score (0–100), a one-sentence reasoning, and a hallucination flag.

Scoring Rubric

90–100
Near-identical meaning, no hallucinations
70–89
Most info present, minor omissions
50–69
Partially correct, some missing info
0–49
Significant misalignment or hallucination

Pass Threshold

A test case passes the semantic check if the score is 50 or above. A score below 50 causes the test to fail with the reason "Semantic score below threshold (50)".

Hallucination Detection

The judge is also instructed to flag hallucinations — cases where the agent's response contains specific facts, numbers, names, or claims that are not present in the golden response and not inferable from the prompt. A hallucinated response fails the test immediately.

Available Judge Models

ModelSpeedContextBest For
Llama 3.3 70B VersatilePowerful128kDeep analysis, highest accuracy
Llama 3.1 8B InstantFast128kQuick checks, high volume
Llama 3 70BBalanced8kStrong reasoning, compact
Llama 3 8BFast8kLightweight, very fast
Gemma 2 9BFast8kGoogle's efficient model
⚠️
Automatic fallback

If a previously selected judge model is decommissioned by Groq, AgentTest automatically retries with the default model (Llama 3.3 70B) instead of failing with an error.

Agent Comparison (Benchmarking)

The Compare Agents page allows you to select any two completed runs and benchmark them against each other across multiple dimensions. This is useful when you want to compare two versions of the same agent, or two completely different agents, on the same set of tests.

Benchmark Dimensions

DimensionWeightHow It's Calculated
Accuracy35%Pass rate (% of test cases passed)
Semantic Quality35%Average semantic score across all test cases
Token Efficiency15%max(0, 100 − avgTokens ÷ 15)
Step Speed15%max(0, 100 − avgSteps × 8)

Overall Score Formula

Overall = 0.35 × Accuracy + 0.35 × SemanticQuality + 0.15 × Efficiency + 0.15 × Speed

What the Report Shows

  • Agent Cards — side-by-side profile cards for each agent showing suite name, agent URL, pass rate, avg semantic score, token usage, steps, and judge model
  • Winner Badge — the winning agent gets a highlighted ring border and "Winner" badge
  • Benchmark Bars — visual score bars for each dimension with a winner indicator
  • Per-Test Breakdown — a table showing pass/fail, semantic score, and token count for both agents on each shared test case
📈
Ties are handled gracefully

If two scores are within 2 points of each other on any dimension, it's declared a tie rather than forcing a winner — preventing misleading conclusions from small differences.

Code Checker

The Code Checker is a built-in tool that lets you submit code (either typed or uploaded as files) and have it analyzed by an AI model for issues, improvements, and best practices.

Data Flow — How a Test Run Works

The following sequence describes exactly what happens from the moment a user clicks "Run Suite" to when the final report is ready:

#EventWhere It Happens
1User clicks "Run Suite" → POST /api/runsBrowser → Server
2Server creates a testRuns record with status "running"Server → Neon DB
3Browser opens an EventSource to /api/stream/{runId}Browser → Server (SSE)
4For each test case, server POSTs to the agent URL with the trigger promptServer → Agent
5Agent responds with trace, response text, token count, step countAgent → Server
6Server emits trace_captured SSE eventServer → Browser
7Server evaluates all assertions, emits assertions_evaluatedServer → Browser
8If golden response exists, server calls Groq judge APIServer → Groq
9Server emits semantic_scored with score + reasoningServer → Browser
10Server writes final result to testResults tableServer → Neon DB
11Server emits test_completed with pass/fail statusServer → Browser
12After all tests, server emits run_completed and closes SSEServer → Browser
13Browser shows "View Full Report" buttonBrowser

SSE Stream Architecture

The streaming is implemented using the Web Streams API (ReadableStream). A closed flag guards against writing to a stream after the client has disconnected — preventing the ERR_INVALID_STATE crash that would otherwise occur if a user navigates away mid-run.

Deploying to Vercel

AgentTest is optimized for Vercel deployment. Follow these steps:

  1. Push your repository to GitHub
  2. Import the repo in Vercel Dashboard → Add New Project
  3. Add the following Environment Variables in Vercel Settings:
VariableDescriptionRequired
DATABASE_URLNeon PostgreSQL connection string (with ?sslmode=require)Yes
GROQ_API_KEYAPI key from console.groq.comYes
NEXT_PUBLIC_APP_URLYour full Vercel URL e.g. https://myapp.vercel.appRecommended
🔗
Mock agent on Vercel

When creating a suite on Vercel, use /api/mock-agent (relative path) as the agent URL instead of http://localhost:3000/api/mock-agent. The agent runner automatically resolves relative paths using the Vercel deployment URL. Existing suites with localhost URLs also auto-correct.

Environment Variable Priority

The agent URL resolver checks variables in this order:

NEXT_PUBLIC_APP_URL  →  https://{VERCEL_URL}  →  http://localhost:3000

Mock Agent (Built-in)

AgentTest ships with a built-in mock AI agent at /api/mock-agent. This lets you try the framework immediately without connecting a real AI agent.

How the Mock Agent Works

The mock agent analyzes keywords in the trigger prompt to select appropriate tools and generate a contextually relevant response. It supports three modes:

Mode (query param)Behavior
?mode=normal (default)Keyword-based tool selection, domain-aware response generation
?mode=failReturns wrong tools and an error-like response for testing failure scenarios
?mode=hallucinateReturns a response with fabricated facts for testing hallucination detection

Domain-Aware Responses

The mock agent generates different responses based on prompt keywords:

  • escalation / critical / urgent → ticket escalation response
  • search / find / lookup → knowledge base search response
  • summarize / brief → summarization response
  • classify / intent → intent classification response
  • validate / verify → validation response
  • format / convert → formatting response
